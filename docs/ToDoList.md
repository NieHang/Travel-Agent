本文整理当前认证、会话管理、聊天流和旅行面板中的未解决问题。依据为代码静态检查与相关测试用例阅读，未运行测试或做线上复现。下列验收标准是待完成工作的目标，不代表已经验证。

## P0：接口权限边界

### [ ] TODO-01 隔离实验接口并补齐用户归属校验

- **现状与影响**：主聊天路径会校验会话归属，但 `AdvancedModule` 同时注册 Memory、Agents 等实验接口。Memory 历史读取和删除使用客户端传入的 `sessionId`，内存历史仅以 `sessionId` 为键；没有绑定当前用户。全局 JWT 只确认已登录，知道同一 `sessionId` 的其他登录用户可访问或清理历史。
- **建议**：明确实验接口是否需要对普通用户开放；不需要的从生产入口禁用。保留的接口必须绑定当前用户并校验资源归属，同时检查参数校验、限流和访问权限是否与主接口一致。
- **验收**：用户 B 无法读取、修改或删除用户 A 的 Memory 历史；伪造 `sessionId` 不能越权；生产入口的实验接口开放范围明确并有对应测试。
- **代码**：`services/chat/src/llm/advanced.module.ts`、`services/chat/src/llm/advanced.controller.ts`、`services/chat/src/llm/memory/runnable-memory.service.ts`。

## P1：聊天可靠性与旅行产品闭环

### [ ] TODO-02 为发送消息增加幂等机制

- **现状与影响**：发送请求只有 `content`。用户消息已经落库但响应丢失时，再次发送可能产生重复消息和重复模型生成；前端防重复点击不能解决网络重试或多端提交。
- **建议**：引入客户端消息 ID 或幂等键，由数据库约束保证去重；明确同键同内容与同键不同内容的行为，并定义重复请求如何查询已有生成。
- **验收**：同一请求并发提交或在断线后重试，只保存一条用户消息、只启动一次生成；不同内容误用同一键得到明确错误。
- **代码**：`packages/contracts/src/chat.ts`、`services/chat/src/chat/chat.service.ts`、`services/chat/prisma/schema.prisma`。

### [ ] TODO-03 定义同一会话的并发生成规则

- **现状与影响**：`useChatStream` 只限制当前 Hook 的重复发送，服务端聊天路径没有同会话生成协调。多个标签页同时发送可能让上下文与回复顺序交错。
- **建议**：先选择“已有生成时拒绝新请求”或“按会话排队”的产品规则，再由服务端落实；协调方式必须匹配部署实例数量。
- **验收**：同一会话的并发请求遵守明确规则，不出现未定义的交错回复；不同会话仍能并行处理。
- **代码**：`clients/chat-web/features/chat/use-chat-stream.ts`、`services/chat/src/chat/chat.service.ts`。

### [ ] TODO-04 建立用户消息、生成记录与助手消息的明确关联

- **现状与影响**：消息模型没有生成 ID 或回复目标字段。前端通过临时 ID 和相邻消息位置推断本地回复是否已有服务端记录；并发、重试和重新生成会增加歧义。
- **建议**：增加生成记录及明确关联，区分消息内容状态和生成执行状态；让前端按关联替换临时消息，设计生成状态查询契约。
- **验收**：每次生成能定位输入消息、执行状态和输出消息；恢复与临时消息替换不依赖消息相邻关系。
- **代码**：`services/chat/prisma/schema.prisma`、`packages/contracts/src/chat.ts`、`clients/chat-web/features/conversations/queries.ts`。

### [ ] TODO-05 补充进程崩溃后的生成恢复

- **现状与影响**：助手文本主要在生成结束、失败或中止时保存。进程崩溃无法保证执行 `finally`，用户已看到的文本可能没有落库，用户消息也可能没有对应助手结果。
- **建议**：在生成记录基础上保存必要检查点，定义失联生成的超时判定和清理规则；明确已生成部分是否保留、恢复还是标记失败。
- **验收**：模拟进程终止并重启后，未结束的生成可识别并收敛到明确状态；界面不会永久等待，已保存部分可以查询。
- **依赖**：TODO-04。
- **代码**：`services/chat/src/chat/chat.service.ts`、`services/chat/prisma/schema.prisma`。

### [ ] TODO-06 接通真实旅行数据与面板

- **现状与影响**：`ChatScreen` 使用 `getTripMock()` 提供旅行面板数据，“保存旅行”按钮仅显示提示。聊天文本、需求卡片与计划、酒店、路线等面板尚未形成真实业务闭环。
- **建议**：先定义旅行对象、需求状态、计划版本和归属规则，再设计读取、修改与保存接口；聊天和面板读取同一份业务状态。
- **验收**：修改目的地、天数、预算等条件后，真实旅行状态和面板一致更新；保存后重新打开能恢复，数据按用户隔离，示例数据与真实数据有明确区分。
- **代码**：`clients/chat-web/features/chat/ChatScreen.tsx`、`clients/chat-web/features/panels/TripPanels.tsx`、`packages/contracts/src/requirement.ts`。

### [ ] TODO-07 改进模型上下文选择

- **现状与影响**：聊天历史固定取最近 20 条非空消息，不按 Token 预算选择，也不排除非空的 `partial`、`error` 消息。早期旅行条件可能丢失，未完成回复可能成为后续上下文。
- **建议**：明确异常消息进入上下文的规则，按 Token 预算组织历史，并使用持久化旅行状态或摘要保留关键条件。
- **验收**：长会话仍保留关键旅行条件；上下文不超出配置预算；异常回复是否保留遵守明确规则并有场景测试。
- **代码**：`services/chat/src/chat/chat.service.ts` 的 `loadHistory()`、`services/chat/src/llm/chat-reply/model-chat-reply.ts`。

## P2：接口一致性、体验与维护性

### [ ] TODO-08 统一普通 JSON 响应的运行时校验

- **现状与影响**：共享 contracts 已提供 Zod Schema，但 `api<T>()` 通过 `as T` 返回 JSON；普通登录、会话等响应没有统一验证。刷新响应和 SSE 事件已使用 Schema 校验。
- **建议**：让 API 封装接收响应 Schema，并逐步覆盖认证、用户、会话和消息分页接口；统一契约不匹配时的错误表示。
- **验收**：错误字段、错误类型和缺失字段在 API 边界被识别，不以合法类型进入组件与缓存；`204` 无响应体仍正常处理。
- **代码**：`clients/chat-web/features/auth/api-client.ts`、`clients/chat-web/features/auth/session.ts`、`clients/chat-web/features/conversations/api.ts`、`packages/contracts/src/`。

### [ ] TODO-09 区分认证刷新失败与临时网络故障

- **现状与影响**：刷新失败会将状态置为 guest，网络异常也会走该路径。短暂断网或后端临时不可用可能表现为退出登录。
- **建议**：区分凭证失效、Token 重用、网络故障和服务端临时故障；明确可恢复状态与重试策略，保持账号切换和登出优先于迟到请求的现有保证。
- **验收**：凭证失效或重用时正确退出；临时网络故障得到明确的可恢复反馈；重试不能覆盖用户主动登出或切换账号。
- **代码**：`clients/chat-web/features/auth/refresh.ts`、`clients/chat-web/features/auth/auth-store.ts`。

### [ ] TODO-10 明确需求抽取的用途与完成时机

- **现状与影响**：需求结果用于卡片展示和消息元数据保存，没有参与回复生成或持续维护旅行需求。回复结束后可能额外等待抽取最多 15 秒，辅助功能延长整次聊天完成时间。
- **建议**：先决定它是辅助展示还是旅行状态输入。如果仅作展示，评估独立完成、补写结果和查询契约；如果用于业务决策，定义增量合并、冲突处理和用户确认规则。
- **验收**：抽取与聊天完成的关系明确；抽取失败不导致无限等待；持久化结果和重新进入页面后的显示一致；明确是否影响后续规划。
- **代码**：`services/chat/src/chat/chat.service.ts`、`services/chat/src/llm/requirement.service.ts`、`clients/chat-web/features/chat/RequirementCards.tsx`。

### [ ] TODO-11 拆分聊天流与缓存协调逻辑

- **现状与影响**：`useChatStream` 同时处理读流、事件、认证变化、中止和缓存写入；`ChatScreen` 同时负责创建会话、发送、错误反馈与视图协调。新增恢复或多任务功能时维护成本会继续增长。
- **建议**：按职责提取事件状态转换、生成恢复和缓存协调模块；保留现有 Hook 的易用入口，避免仅按文件长度机械拆分。
- **验收**：拆分前后行为一致，继续覆盖停止、切换会话、切换账号、迟到分页和临时消息对齐；组件不承担底层流协议处理。
- **代码**：`clients/chat-web/features/chat/use-chat-stream.ts`、`clients/chat-web/features/chat/ChatScreen.tsx`、`clients/chat-web/features/conversations/queries.ts`。

### [ ] TODO-12 加固长连接传输

- **现状与影响**：当前 SSE 写出未见显式心跳或等待 `res.write()` 背压的处理。长时间无输出、慢客户端和代理缓冲下的表现尚未验证。
- **建议**：结合实际部署链路定义心跳、超时、背压及代理缓冲策略，保持连接关闭时取消模型调用的现有行为。
- **验收**：在慢客户端和长时间无文本输出场景下，连接按规则保持或结束，缓冲受控；中止后及时清理请求；在实际代理配置下验证流式输出。
- **代码**：`services/chat/src/chat/chat.controller.ts`。

## P3：按需求推进的能力与架构决策

### [ ] TODO-13 评估流断线后的续读能力

- **触发条件**：产品要求断线后继续同一次生成，而非停止并重新查询消息。
- **现状**：没有事件 ID、事件重放或流恢复接口；当前通过历史查询和临时消息轮询对齐服务端。
- **建议**：基于生成 ID 定义事件序号、保留时间和续读协议；同时明确“主动停止”与“暂时掉线”是否应采用不同执行规则。
- **验收**：断线后不会重复发起生成，重放不重复追加文本；过期事件有明确回退路径；主动停止仍按产品规则生效。
- **依赖**：TODO-04、TODO-05。

### [ ] TODO-14 为多实例部署提供一致的限流与协调

- **触发条件**：后端从单实例扩展到多实例。
- **现状**：限流计数使用实例内存；本地协调不能自动跨实例生效。
- **建议**：采用共享计数存储，并保证幂等与会话并发策略跨实例有效；只有出现需要脱离连接持续执行的长任务时，再引入后台任务机制。
- **验收**：同一用户跨实例请求遵守统一额度；同一幂等键不会跨实例重复生成；会话并发规则一致。
- **依赖**：TODO-02、TODO-03。
- **代码**：`services/chat/src/app.module.ts`、`services/chat/src/auth/app-throttler.guard.ts`。

### [ ] TODO-15 明确 Access Token 撤销时效

- **触发条件**：产品需要退出登录、用户禁用或会话撤销后，立即阻止已签发 Access Token 的使用。
- **现状**：JWT Guard 只验签名与过期时间，不查询会话撤销状态；退出吊销刷新链，已有 Access Token 在过期前仍可通过校验，默认有效期为 15 分钟。这是当前策略的限制，不等同于刷新链吊销无效。
- **建议**：明确是否接受短有效期策略；若要求立即撤销，再评估会话版本、撤销记录或服务端会话检查及其查询成本。
- **验收**：文档明确退出和撤销的生效时间；若要求立即撤销，旧 Access Token 在撤销后按规则拒绝。
- **代码**：`services/chat/src/auth/jwt-auth.guard.ts`、`services/chat/src/auth/access-token.service.ts`、`services/chat/src/auth/auth.service.ts`、`services/chat/src/config/auth.config.ts`。

### [ ] TODO-16 评估私有页面的认证恢复体验

- **触发条件**：启动加载时间或私有页面首屏体验成为实际问题。
- **现状**：前端启动后刷新认证，`AuthGate` 在登录态恢复前显示加载界面；浏览器直接调用跨源后端，当前没有承担私有数据认证中转的 BFF。
- **建议**：先测量认证恢复与首屏耗时，优先优化现有路径；只有收益明确时，再评估同源代理、BFF 或服务端会话方案。
- **验收**：用测量结果说明改动收益；保留账号隔离、刷新与登出正确性；部署和 Cookie 规则有明确说明。
- **代码**：`clients/chat-web/app/providers.tsx`、`clients/chat-web/features/auth/AuthGate.tsx`、`clients/chat-web/next.config.ts`。
