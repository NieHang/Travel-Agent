# 日本旅行规划 Skill 设计

日期：2026-10-18（同日修订，见文末"修订记录"）

## 背景与目的

Hilda 现在的行程规划只有一条粗略的提示词（`services/chat/src/trip/llm.ts` 的 `TASKS.itinerary`）：先搜酒店，再按天写 Markdown 草稿。节奏、地理顺路、交通、开放时间、季节都没有涉及，输出离"能照着走"的行程差得远。

Hilda 只做日本行程。这个设计给 Hilda 加一组日本旅行规划 skill：

- 一个**核心 skill**：写明怎么排日本路线、排出来要达到什么程度。每个规划和问答回合都加载。
- 若干**城市 skill**：每个城市一个，只写这个城市的差异（区域划分、机场进出、一日游、交通卡等）。由**模型自己决定**读哪些，通过 `load_skill` 工具按需加载。

加载机制是通用的：新增一个城市就是在 `skills/` 下多放一个文件夹，不改代码。

## 目标

1. 新增 `services/chat/skills/japan-travel/`（核心）和第一批城市 skill：`japan-tokyo`、`japan-kyoto`、`japan-osaka`、`japan-nara`。
2. 核心 skill 在 `answer` 和 `itinerary` 两个任务里**总是加载**，全文放进系统提示词。
3. 其余 skill 在系统提示词里列出名称和描述，并提供 `load_skill` 工具（LangChain 文档中的 skills 模式，自己实现），由模型决定加载哪些。
4. 自己实现，不引入 LangChain Deep Agents：它会接管工具循环，与"服务端掌控流程、LLM 只做语言工作"的架构以及 `show_results` 的来源核对冲突，额外的规划/文件系统工具也会占用提示词和工具轮次。等 skill 规模大到需要嵌套管理、需要执行脚本或子 agent 时再评估。

## 非目标（第一版不做）

- 不接真实的交通、餐厅、景点数据。交通时间由模型估算并标注"约"。
- 不改 `packages/contracts`、需求表单、右侧面板、前端任何代码。每天的强度、交通段、"出发前要办"清单都只体现在 Markdown 草稿正文里。
- 不新增需求字段（如"节奏"）。节奏从用户填写的偏好里读，读不到按"标准"。
- 不执行 Python 脚本（见"脚本"一节）。
- 不处理非日本目的地：不做按目的地匹配，不为非日本行程保持提示词不变。用户填了非日本目的地时，模型照样按日本规则写，结果未定义。
- 服务端不兜底城市加载：模型没调用 `load_skill` 时不自动注入城市内容，靠提示词和实时检查保证。

## 反目标（技术上能跑但算失败的情况）

- 输出的行程没有按核心 skill 的标准写（没有总览、没有交通段、首尾日排满）。
- 行程涉及东京、大阪等已有城市 skill 的城市，模型却没有加载对应 skill。
- 估算的交通时间被写成确定的事实（没有"约"）。
- 为了交通段，模型开始编造价格、营业时间、地址或酒店。估算只放宽到**交通时长、步行距离和换乘**，其他规则不变。
- 加了 skill 后，右侧面板的每日行程把"坐银座线到上野"这类交通段当成景点显示出来。
- 加载 skill 占掉工具轮次，导致酒店搜索或 `show_results` 没来得及调用。

## 验收标准（核心 SKILL.md 要让模型达到的输出）

一份合格的日本行程草稿包含：

1. **总览**：城市顺序和每城晚数（如"东京 3 晚 → 京都 2 晚"）、换酒店次数、每天强度一览。
2. **每天一个主题区域和强度**（轻松 / 标准 / 较累）。
3. **时间线**：每个站点有时间；站点之间写清交通方式、线路、约多少分钟、换乘次数。
4. **吃饭和休息**排在时间线里。
5. **理由**：与用户偏好相关的安排说明为什么这样排。
6. **出发前要办**：需要预约的地方、交通卡等，单独列出。
7. **备选**：雨天替代、太累时可砍掉的项目。
8. **诚实**：估算标"约"，不确定的提醒用户确认。

规划规则（核心 SKILL.md 内容要点，具体写法留给实现者）：

- **体力与节奏**：到达日、离开日只安排轻松活动；每天 2–3 个主要景点，按节奏浮动；累的一天后接轻松的一天。
- **地理顺路**：同一半天只在一个区域；一天内站点顺路串联，不折返；城市顺序跟随航班，鼓励东京进大阪出这类开口行程。
- **少换酒店**：每城至少 2–3 晚，周边用一日游覆盖；需要换酒店时提醒行李寄送（宅急便）。
- **交通**：每段给出线路、约多少分钟、换乘次数；尽量不超过一次换乘；避开早高峰，带行李时尤其要避开；建议使用 IC 卡；城际交通用新干线；JR Pass 需按行程判断是否划算，不默认推荐；单独说明机场到市区的交通。
- **开放时间与预约**：注意周一闭馆、寺社傍晚关门；需要预约的热门项目列入"出发前要办"；热门景点建议早到。
- **季节**：樱花、红叶、黄金周、盂兰盆节的拥挤；梅雨季、台风季准备雨天备选。
- **留余量**：不排满，留休息和意外时间。
- **城市 skill**：写行程或回答具体城市的问题之前，先用 `load_skill` 加载要住的城市和一日游城市的 skill。

城市相关的具体内容（哪些区域适合放在同一天、某机场怎么进城、某城的交通卡）不写在核心里，放进城市 skill。

**开放时间、距离的写法**（我的决定）：可以写广为人知的一般规律，但必须用"通常/一般……出发前请确认"的语气，例如"多数寺社 17:00 左右关门，出发前请确认"。不能给具体某个景点写出确切的营业时间。步行距离同交通时长一样，可以估算并标"约"（如"步行约 10 分钟"）。

**参考示例**（对话中用户认可的验收样例，可整理后放进核心 SKILL.md）：情侣，6 天 5 晚，东京进、大阪出，标准节奏。

> **总览**：东京 3 晚 → 京都 2 晚 → 关西机场离开｜换酒店 1 次｜强度：轻 · 标准 · 标准 · 较累 · 标准 · 轻
>
> **出发前要办**：teamLab Planets 提前 2 周预约｜到达后在机场办 Suica 卡
>
> **Day 1｜到达 · 上野/浅草（轻松）**
> - 14:00 成田机场 → 京成 Skyliner 到上野，约 45 分钟，不用换乘
> - 15:30 酒店入住，休息一下
> - 17:00 浅草寺、仲见世通（银座线 1 站，约 5 分钟），傍晚亮灯，人比白天少
> - 19:00 浅草附近吃晚饭，早点回去睡
> - 今晚住：上野 XX 酒店
>
> **Day 4｜东京 → 京都 · 伏见稻荷（较累）**
> - 09:00 退房，行李用宅急便寄到京都酒店
> - 10:00 东京站坐新干线 Nozomi 到京都，约 2 小时 15 分钟
> - 14:00 JR 奈良线 1 站到稻荷，约 5 分钟；千本鸟居登顶来回约 2–3 小时，累了半山腰就可以回头
> - 雨天备选：改去京都站附近的三十三间堂（室内）
>
> **Day 6｜离开（轻松）**
> - 上午只在酒店附近吃早餐、买伴手礼
> - 11:30 京都站坐 Haruka 到关西机场，约 75 分钟，留足时间值机

注意：示例里的酒店在真实草稿中必须来自酒店工具结果，示例只是展示格式。

## 已确定的方案

### 目录（用户确定）

核心一个 skill，每个城市各一个 skill，平级放在 `skills/` 下，城市 skill 加 `japan-` 前缀：

```
services/chat/skills/
├── japan-travel/            # 核心，always: true
│   ├── SKILL.md
│   └── scripts/
│       ├── traffic_routes.py
│       └── restaurants_info.py
├── japan-tokyo/SKILL.md
├── japan-kyoto/SKILL.md
├── japan-osaka/SKILL.md
└── japan-nara/SKILL.md
```

### SKILL.md 格式

- 开头用 YAML frontmatter：
  - `name`：与文件夹名一致。
  - `description`：一句话，放进系统提示词的 skill 列表，让模型判断要不要加载。城市 skill 写清城市名（中英文）和内容范围，如"Tokyo (东京): areas, airports, day trips, transit cards"。
  - `always`：可选，`true` 表示总是加载。只有核心 skill 设置。
- 正文用英文（现有提示词都是英文，输出语言由 locale 决定）。

### 加载方式

1. **启动时扫描**：读取 `skills/*/SKILL.md`，解析 frontmatter 并缓存。解析失败的 skill 记一条日志后跳过，不能影响启动；`skills/` 不存在时没有 skill。
2. **总是加载**：`always: true` 的 skill 在 `answer` 和 `itinerary` 任务里把全文放进系统提示词。`classify` 不加载。
3. **模型控制加载**：其余 skill 在 `answer` 和 `itinerary` 任务里以"名称: 描述"列在系统提示词中，同时绑定本地工具 `load_skill`（和 `show_results` 一样不走 MCP）：
   - 参数是名称数组，一次可加载多个城市；返回各 skill 正文。未知名称返回可用名称列表，不抛异常。
   - 提示词要求模型在**第一轮**把 `load_skill` 和酒店搜索一起并行调用，不单独占一轮。`MAX_TOOL_ROUNDS` 目前是 4，实时检查发现不够再调到 5。
   - **作用时长**：只对当次模型调用有效，不持久化，不写入 `state.toolResults`（以免挤掉酒店结果），也不截断、不压缩。下一回合需要时模型再读一次；读的是内存里的缓存，成本很低。*（我的决定）*
   - 没有非 always 的 skill 时，不出现列表和工具。
4. **估算规则**：现有系统提示词写着 "Never invent prices, availability, addresses or distances"。加载核心 skill 后改写这句基础规则（而不是在后面追加一句相反的话）：交通时长、步行距离和换乘可以估算，但必须标"约"/"approx."；价格、可用性、地址、具体营业时间仍然不能编造。
5. **`extractDays`**：提取提示词加一句"交通段不是站点，并入它通往的那一站的备注"。因为只做日本，这条总是生效，不需要传目的地。

### 城市 skill 内容

每个城市 skill 只写该城市的差异，不重复核心规则。建议结构（具体措辞留给实现者）：

- **区域划分**：主要区域，哪些适合放在同一个半天/一天。
- **进出城**：机场或主要车站到市区的方式、约多少分钟。
- **城内交通**：主力线路、交通卡、需要注意的换乘。
- **常见一日游**：从该城出发的一日游及大致交通。
- **预约与人流**：需要提前预约的热门项目、建议早到的地方。
- **季节**：该城特有的季节看点和拥挤时段。

具体营业时间、价格不写；一般规律用"通常……出发前请确认"的语气。每个城市 skill 目标在约 1500 token 以内。

### 脚本

- *（我的方案）* 第一版在核心 skill 下创建 `traffic_routes.py`、`restaurants_info.py` 两个占位文件，只写注释，说明以后的用途和打算采用的 JSON 输入输出约定。不实现、不暴露执行工具，`SKILL.md` 也不提到它们，以免模型去调用不存在的能力。
- 以后接入时的方向（不在本次范围）：由后端以子进程调用 Python，JSON 进 JSON 出，结果作为工具结果返回，以便沿用 `results.ts` 对工具结果的来源核对。

### 代码边界

- 读文件系统、解析 frontmatter 的加载代码不放在 `state` / `commands` / `view` 里，这几个文件必须保持不依赖 Nest、Prisma、LangChain。
- `skills/` 目录的定位方式要在 `bun run dev`、构建后的 `dist` 运行、单元测试三种情况下都能找到。具体做法留给实现者。

## 约束与已知风险

- **输出长度**：`config/langchain.yaml` 的 `maxTokens: 4096`。按验收标准写的 6–7 天中文行程可能超出，会被截断。实现者需要用真实模型测一次，必要时调高上限，或者在核心 SKILL.md 里控制详细程度（例如长行程只把最关键的交通段写全）。
- **提示词体积**：核心 skill 每次请求都带上，目标在约 3000 token 以内；城市 skill 按需加载，每个约 1500 token 以内。这两个上限是我的估计，实现者可以调整。
- **模型不加载城市 skill**：当前模型是 DeepSeek flash（`temperature: 0`），可能跳过 `load_skill`。服务端不兜底，所以实时检查必须断言东京进大阪出的用例加载了 `japan-tokyo` 和 `japan-osaka`；不通过就改提示词。
- **工具轮次**：写行程要搜酒店（多城时每城一次）和 `show_results`，再加 `load_skill` 可能超过 4 轮。见"加载方式"第 3 条。
- **面板解析**：`extractDays` 把草稿解析成每天的站点。草稿里加了交通段以后，要确保交通段不被解析成站点。这是"不改面板"这一目标能否成立的前提。

## 验证

- **单元测试**：
  - frontmatter 解析，包括缺字段、格式坏掉时跳过，`always` 默认为否。
  - `always` skill 的正文出现在 `answer` / `itinerary` 系统提示词里，`classify` 没有。
  - 非 always skill 以"名称: 描述"列出，`load_skill` 已绑定；没有非 always skill 时两者都不出现。
  - `load_skill` 返回所请求 skill 的正文；未知名称返回可用列表而不是抛出异常。
  - `load_skill` 的结果不进入 `toolResults`，长度超过 `MAX_RESULT_LENGTH` 也不被截断或压缩。
  - 随仓库发布的 skill：五个都能解析，核心是 always，城市不是；体积在上限内；正文不提 `.py`。
- **改构造函数要同步改测试**（LESSON.md）：`ModelTripLlm` 新增依赖时，所有构造它的测试和 `scripts/test-trip-live.ts` 要在同一个提交里一起改。
- **真实运行**（CLAUDE.md 约定）：`scripts/test-trip-live.ts` 原有的杭州用例换成日本目的地，并加东京进大阪出的用例（中英各一，"2026-12-01 到 2026-12-06，2 人"），至少检查：
  - 加载了 `japan-tokyo` 和 `japan-osaka`
  - 找到了酒店（加载 skill 没有挤掉酒店搜索）
  - 草稿包含总览和"出发前要办"
  - 出现"约"或"approx"
  - `days` 覆盖每一天，且没有把交通段当成站点
- **人工抽查**：读一份真实生成的日本草稿，对照验收标准 8 条逐条看。
