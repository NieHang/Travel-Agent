# 日本旅行规划 Skill 设计

日期：2026-10-18

## 背景与目的

Hilda 现在的行程规划只有一条粗略的提示词（`services/chat/src/trip/llm.ts` 的 `TASKS.itinerary`）：先搜酒店，再按天写 Markdown 草稿。节奏、地理顺路、交通、开放时间、季节都没有涉及，输出离"能照着走"的行程差得远。

这个设计给 Hilda 加一个**日本旅行规划 skill**：一份写明"怎么排日本路线、排出来要达到什么程度"的说明。用户的目的地是日本时，Hilda 必须按它来写行程。同时建立一套通用的 skill 加载机制，以后其他国家、以及获取交通/餐厅/景点数据的 Python 脚本，都放进同一套结构里。

## 目标

1. 新增 `services/chat/skills/japan-travel/`，其中 `SKILL.md` 写清日本路线的规划规则和输出标准（见下文"验收标准"）。
2. 后端在目的地属于日本时**强制加载**这个 skill，把 `SKILL.md` 全文放进系统提示词。
3. 实现 LangChain 文档中的 skills 模式（自定义实现）：系统提示词列出可用 skill 的名称和描述，提供 `load_skill` 工具，让模型在未被强制加载时按需加载。
4. 加载机制是通用的：新增一个 skill 就是在 `skills/` 下多放一个文件夹，不改代码。

## 非目标（第一版不做）

- 不接真实的交通、餐厅、景点数据。交通时间由模型估算并标注"约"。
- 不改 `packages/contracts`、需求表单、右侧面板、前端任何代码。每天的强度、交通段、"出发前要办"清单都只体现在 Markdown 草稿正文里。
- 不新增需求字段（如"节奏"）。节奏从用户填写的偏好里读，读不到按"标准"。
- 不执行 Python 脚本（见"脚本"一节）。

## 反目标（技术上能跑但算失败的情况）

- 目的地是日本，但输出的行程没有按 skill 的标准写（没有总览、没有交通段、首尾日排满）。
- 估算的交通时间被写成确定的事实（没有"约"）。
- 为了交通段，模型开始编造价格、营业时间、地址或酒店。估算只放宽到**交通时长和换乘**，其他规则不变。
- 加了 skill 后，右侧面板的每日行程把"坐银座线到上野"这类交通段当成景点显示出来。
- 非日本目的地的行程因为这次改动变差或变化。

## 验收标准（SKILL.md 要让模型达到的输出）

一份合格的日本行程草稿包含：

1. **总览**：城市顺序和每城晚数（如"东京 3 晚 → 京都 2 晚"）、换酒店次数、每天强度一览。
2. **每天一个主题区域和强度**（轻松 / 标准 / 较累）。
3. **时间线**：每个站点有时间；站点之间写清交通方式、线路、约多少分钟、换乘次数。
4. **吃饭和休息**排在时间线里。
5. **理由**：与用户偏好相关的安排说明为什么这样排。
6. **出发前要办**：需要预约的地方、交通卡等，单独列出。
7. **备选**：雨天替代、太累时可砍掉的项目。
8. **诚实**：估算标"约"，不确定的提醒用户确认。

规划规则（SKILL.md 内容要点，具体写法留给实现者）：

- **体力与节奏**：到达日、离开日只安排轻松活动；每天 2–3 个主要景点，按节奏浮动；累的一天后接轻松的一天。
- **地理顺路**：同一半天只在一个区域；一天内站点顺路串联，不折返；城市顺序跟随航班，鼓励东京进大阪出这类开口行程。
- **少换酒店**：每城至少 2–3 晚，周边用一日游覆盖；需要换酒店时提醒行李寄送（宅急便）。
- **交通**：每段给出线路、约多少分钟、换乘次数；尽量不超过一次换乘；避开早高峰，带行李时尤其要避开；建议使用 IC 卡（Suica / ICOCA）；城际交通用新干线；JR Pass 需按行程判断是否划算，不默认推荐；单独说明机场到市区的交通。
- **开放时间与预约**：注意周一闭馆、寺社傍晚关门；需要预约的热门项目列入"出发前要办"；热门景点建议早到。
- **季节**：樱花、红叶、黄金周、盂兰盆节的拥挤；梅雨季、台风季准备雨天备选。
- **留余量**：不排满，留休息和意外时间。

**开放时间、距离的写法**（我的决定）：可以写广为人知的一般规律，但必须用"通常/一般……出发前请确认"的语气，例如"多数寺社 17:00 左右关门，出发前请确认"。不能给具体某个景点写出确切的营业时间。步行距离同交通时长一样，可以估算并标"约"（如"步行约 10 分钟"）。

**参考示例**（对话中用户认可的验收样例，可整理后放进 SKILL.md）：情侣，6 天 5 晚，东京进、大阪出，标准节奏。

> **总览**：东京 3 晚 → 京都 2 晚 → 关西机场离开｜换酒店 1 次｜强度：轻 · 标准 · 标准 · 较累 · 标准 · 轻
>
> **出发前要办**：teamLab Planets 提前 2 周预约｜到达后在机场办 Suica 卡
>
> **Day 1｜到达 · 上野/浅草（轻松）**
> - 14:00 成田机场 → 京成 Skyliner 到上野，约 45 分钟，不用换乘
> - 15:30 酒店入住，休息一下
> - 17:00 浅草寺、仲见世通（银座线 1 站，约 5 分钟），傍晚亮灯，人比白天少
> - 19:00 浅草附近吃晚饭，早点回去睡
> - 今晚住：上野 XX 酒店
>
> **Day 4｜东京 → 京都 · 伏见稻荷（较累）**
> - 09:00 退房，行李用宅急便寄到京都酒店
> - 10:00 东京站坐新干线 Nozomi 到京都，约 2 小时 15 分钟
> - 14:00 JR 奈良线 1 站到稻荷，约 5 分钟；千本鸟居登顶来回约 2–3 小时，累了半山腰就可以回头
> - 雨天备选：改去京都站附近的三十三间堂（室内）
>
> **Day 6｜离开（轻松）**
> - 上午只在酒店附近吃早餐、买伴手礼
> - 11:30 京都站坐 Haruka 到关西机场，约 75 分钟，留足时间值机

注意：示例里的酒店在真实草稿中必须来自酒店工具结果，示例只是展示格式。

## 已确定的方案

### 目录（用户确定）

```
services/chat/skills/japan-travel/
├── SKILL.md
└── scripts/
    ├── traffic_routes.py
    └── restaurants_info.py
```

### SKILL.md 格式

- 开头用 YAML frontmatter，至少包含 `name`、`description`（一句话，给 `load_skill` 列表用）。
- *（我的方案）* frontmatter 再加一份目的地匹配词 `match`，覆盖中文、英文、日文的"日本"及主要城市、地区名（如 日本 / Japan / 東京 / 东京 / Tokyo / 京都 / Kyoto / 大阪 / 北海道 / 冲绳 / 沖縄 / Okinawa ...）。匹配不区分大小写，按子串匹配目的地文本；"日本、韩国"这类多国目的地也算匹配。
- 正文是规则和输出标准，用英文写还是中文写留给实现者决定（现有提示词都是英文，输出语言由 locale 决定）。

### 加载方式

1. **启动时扫描**：读取 `skills/*/SKILL.md`，解析 frontmatter 并缓存。解析失败的 skill 记一条日志后跳过，不能影响启动。
2. **强制加载**（用户确定）：`requirements.destination` 命中某个 skill 的 `match` 时，把该 skill 全文放进系统提示词。*（我的方案）* 生成草稿（`itinerary`）和普通聊天（`answer`）两个任务都适用，这样用户追问"第三天换成奈良"时也按同一套规则回答。`classify` 和 `extractDays` 不加载。
3. **按需加载**（LangChain skills 模式）：**只在 `requirements.destination` 为空时**，系统提示词才列出可用 skill（名称 + 描述），工具列表才加 `load_skill(name)` 工具，它返回 `SKILL.md` 正文。用于目的地还没定、用户却在聊日本的情况。目的地已设定时（无论是不是日本）都不出现列表和工具，这样非日本行程的提示词和工具保持不变，也不会多占 `MAX_TOOL_ROUNDS` 的轮次。`load_skill` 是本地工具，和 `show_results` 一样不走 MCP。*（我的决定）*
   - **作用时长**：按需加载只对当次模型调用有效，不持久化，也不写入 `state.toolResults`，以免挤掉酒店结果。理由：一旦用户确定目的地是日本，强制加载就会接管，不需要记住按需加载的状态。*（我的决定）*
4. **估算规则的放宽**：现有系统提示词写着 "Never invent prices, availability, addresses or distances"。加载日本 skill 后，交通时长和换乘可以估算，但必须标"约"/"approx."；价格、可用性、地址、营业时间仍然不能编造。实现时要让这两条规则不互相矛盾（例如加载 skill 时改写这句基础规则，而不是在后面再追加一句相反的话）。

### 脚本

- *（我的方案）* 第一版创建 `traffic_routes.py`、`restaurants_info.py` 两个占位文件，只写注释，说明以后的用途和打算采用的 JSON 输入输出约定。不实现、不暴露执行工具，`SKILL.md` 也不提到它们，以免模型去调用不存在的能力。
- 以后接入时的方向（不在本次范围）：由后端以子进程调用 Python，JSON 进 JSON 出，结果作为工具结果返回，以便沿用 `results.ts` 对工具结果的来源核对。

### 代码边界

- 读文件系统、解析 frontmatter 的加载代码不放在 `state` / `commands` / `view` 里，这几个文件必须保持不依赖 Nest、Prisma、LangChain。
- `skills/` 目录的定位方式要在 `bun run dev`、构建后的 `dist` 运行、单元测试三种情况下都能找到。具体做法留给实现者。

## 约束与已知风险

- **输出长度**：`config/langchain.yaml` 的 `maxTokens: 4096`。按验收标准写的 6–7 天中文行程可能超出，会被截断。实现者需要用真实模型测一次，必要时调高上限，或者在 SKILL.md 里控制详细程度（例如长行程只把最关键的交通段写全）。
- **提示词体积**：强制加载时，每次请求都带上 SKILL.md 全文。SKILL.md 要写得紧凑，目标在约 3000 token 以内（这个上限是我的估计，实现者可以调整）。
- **面板解析**：`extractDays` 把草稿解析成每天的站点。草稿里加了交通段以后，要确保交通段不被解析成站点（例如在提取提示词里说明交通信息并入下一站的备注）。这是"不改面板"这一目标能否成立的前提。
- **模型**：当前是 DeepSeek flash（`temperature: 0`）。规则写得再好，弱模型也可能漏掉。所以验证必须包含真实模型运行。

## 验证

- **单元测试**：
  - frontmatter 解析，包括缺字段、格式坏掉时跳过。
  - 目的地匹配：中、英、日文城市名都要命中；非日本目的地（杭州、Paris）不命中。
  - 强制加载时系统提示词包含 skill 正文、不包含时则没有。
  - `load_skill` 返回正文；名称未知时返回错误信息而不是抛出异常。
  - 目的地已设定且不是日本时，系统提示词和工具列表与改动前完全一致（精确比较）。
  - 目的地为空时出现 skill 列表和 `load_skill`。
- **`extractDays` 的交通段处理**只在加载了 skill 时生效，非日本行程的提取提示词不变。
- **改构造函数要同步改测试**（LESSON.md）：`ModelTripLlm` 如果新增依赖，所有构造它的测试和 `scripts/test-trip-live.ts` 要在同一个提交里一起改。
- **真实运行**（CLAUDE.md 约定）：在 `scripts/test-trip-live.ts` 里加日本用例（中英各一，比如"东京进大阪出 6 天 5 晚，2 人"），至少检查：
  - 草稿包含总览和"出发前要办"
  - 出现"约"或"approx"
  - `days` 里没有把交通段当成站点
  - 原有杭州用例仍然通过
- **人工抽查**：读一份真实生成的日本草稿，对照验收标准 8 条逐条看。
